## 第一步：基准

### 审计标准

以仓库自己定的规则为准，出处是 `docs/ARCHITECTURE.md` 和 `scripts/check_architecture.py`。

- 分层方向：`domain ← application ← storage`（storage 只能引用 `application.ports`）；ui、transport、background、exporting 这几层只能调用 application；`bootstrap.py` 是唯一的装配入口（composition root，所有部件在这里接起来）。
- SQL 只允许出现在 storage。
- 一个业务动作只能有一个负责的模块（下文称 owner）。
- 文件超过 500 行只是黄牌，要看职责，不因行数判罪。

## 第二步：各项审计要点

### 干净的部分（这很重要，决定了不需要重建）

- domain 层只依赖它自己和 `markdown_it`，是纯的。
- ui 和 transport 没有一处引用 storage。
- storage 之外没有 SQL。
- 除了下面列出的，没有发现跨模块调用私有函数。
- 各块的归属：
  - `NoteSidebar`、`ReminderCenter`、`theme.py` 虽然大，但职责单一，判为保持现状。
  - `MainWindow` 1026 行、50 个公开方法，偏胖，但主要是导航和保存状态机，本来就该放在 UI。
  - Gale 本地发布和拉取只有 R2 这一个 owner。
  - legacy 里的 `gale_remote_mcp`、outbox 等是 **Oracle 服务器上正在运行的代码**，不是残留。

### 侵蚀集中在一处：AI 提案「接受」这条链路

也就是 GreenCloud Step 2/3 新加的内容。核心证据如下（关键的几条我亲自对过代码）。

1. **存储层在做业务。** `SQLiteAiMcpOperationRepository` 总共 967 行，其中约 300 行是业务逻辑。
   - `accept_pending_modification` 一个方法约 240 行，里面有收件箱状态机、9 个字段的指纹比对、权限判断、payload 格式校验、重新应用编辑、Qt 规范化。
   - 权限判断 `_actor_can_modify/edit/use_directory` 在 718-751 行，确认策略的默认值在 37-42 行。
2. **Qt 图形组件被放进了数据库写锁里。**
   - `markdown_canonicalizer` 实际上是离屏的 QtWebEngine + Milkdown，会自己创建 `QApplication`，必须在主线程运行，单次等待最长 30 秒，最多跑 4 轮。
   - 它在 `connections.write()` 里被调用，而这个写入一开头就是 `BEGIN IMMEDIATE`（`connection.py:39`，已核实）。
   - 数据库的 `busy_timeout` 只有 5 秒。所以 GUI 自动保存或其他 MCP 写入，都可能在这段时间里撞上「database is locked」。数据不会丢，但会出现一段先卡住、再报失败的窗口。
3. **无界面的 MCP 进程加载了整套 GUI。**
   - `transport/mcp/server.py` 引用了 `bootstrap`，而 `bootstrap.py:9,37` 在文件顶部就引用了 `QApplication` 和 `MainWindow`（已核实）。
   - AI 每次写入都要在 MCP 进程里启动一个 Chromium。
   - 能用只是因为 FastMCP 恰好在主线程调用同步工具。哪天它改成在工作线程调用，所有 AI 写入都会静默变成「无法生成稳定的 Markdown 正文」。
4. **「冲突」这个概念没有 owner。**
   - 存储层把冲突记成 `handling_mode="human_rejected"`（`ai_mcp_operations.py:762-781`）。
   - application 把它变成一个普通的 `ValueError` 抛出去（`ai_receipt_inbox_service.py:433`）。
   - 然后外层自己再补回来：transport 补了两处（`tools.py:967-972, 1006-1011`），`ai_center_dialog.py` 补了三处（210-224、826-847、1262-1270）。
   - 最近 4 个 commit（`9329b32`、`51fce35`、`286b6bc`、`27d6d3d`）都是在外层打补丁，没有回到 owner 去修。
5. **单一真相源失守。**
   - 「完全授权」这个判断有 **4 份实现**，语义还不一致。`local_mcp_service.py:222` 没做 normalize；存储层那份不看 redaction 规则是否可用。
   - 编辑 payload 的校验有 3 份。
   - `ai_operations` 这张操作流水表有 **3 个写入方**：`ai_mcp_operations`、`ai_receipts`、`reminders`。
6. **隐藏协议已经造成一个真 bug（已核实）。**
   - `ai_receipts._store_operation` 写的字段是 `changed`、`pending_confirmation`；`ai_mcp_operations._result` 写的是 `modified_formal_note`、`entered_confirmation`。
   - transport 只读后一套。
   - 结果：人工接受 AI 的 create 提案之后，AI 调 `get_operation_status` 拿到的是 `status=created, changed_formal_note=false`，和事实相反。

### 其他区域

- **Reminder**
  - 状态转换规则只写在 UI 里（`reminder_center.py:564-590`）。service 和 repository 对任何非删除状态都放行。
  - 所以 AI 调 `resume` 可以把一条**已完成**的提醒重新激活，同时清空 `completed_at`（已核实 `reminder_service.py:94` 和 `reminders.py:531-548`）。
  - AI 写入分散在 4 个事务里，不是原子的。
  - `ReminderService` 有 45 个公开方法，同时管 CRUD、标签、表格、AI 闸口、周期计算、通知六件事，是一个在长的 God Object（下称上帝对象）。
- **装配入口**：`gale_bootstrap.py` 和 `reminder_helper.py` 实际上是第二、第三个装配入口，而闸门只放行 `bootstrap.py` 这一个。
- **闸门本身的盲区**
  - 不扫描 `src/snotes/` 顶层文件（`gale_bootstrap`）和 `migration/`。
  - 不拦截对 `src.*` 旧模块的引用。
  - 看不出「不需要 import 的业务逻辑」，也看不出 JSON 格式分叉。
- **测试和结构的关系**
  - 11 个测试文件直接构造存储类来测端到端行为，分不出逻辑属于哪一层。
  - 4 处测试直接 patch 了 ui 层的 `MarkdownCanonicalizer` 具体类，等于把错误的依赖写死成了规格。
  - `test_gc35_helper_import_boundary` 只验证「导入时不加载 GUI」，实际上默许了懒加载式的越层。
- **文档**：`ARCHITECTURE.md` 还写着「storage 未接入 UI」「`src/mcp_server` 是冻结参照」，已经过时。

## 第三步：结论

### 1. 总体定级：明显侵蚀（局部集中）

**为什么不是「早期侵蚀」**

- 闸门红了 10 个 commit 没人管，全量测试红是常态。也就是说防护机制名义上还在，实际上已经失效。
- 侵蚀发生在安全最敏感的 AI 写入链路，而且已经长出一个真 bug（P1-2），还出现了一个权限不变量只由 UI 守着的漏洞（P1-5）。

**为什么远不到「值得重建」**

- 没有 P0。
- domain、ui 和 storage 之间的隔离、SQL 归属这几条主干都完好。
- 问题集中在大约 6 个文件，都是两天之内造成的。
- 每一条都有现成的目标 owner（`ports.py`、`AiReceiptInboxService`）。

### 3. 「修」和「重建」的成本对比

**原地修**：P1 全部做完，大约相当于**一个 Step 2 规模的施工包**。

- 主要工作量在 P1-4（搬走接受逻辑）和测试改写（去掉对具体 ui 类的 patch）。
- 涉及大约 10 个文件。
- 行为可以用现有的 447 个测试和 Step 2/3 的人工验收（human gate）场景回归。

**重建**：R2 本身就是一次重建（8 个 Package + R1 对照），之后又叠加了 Reminder、Gale、Markdown 切换、GreenCloud Step 1-3。

- 重建要重新拿到这些对照测试和人工验收的证据，还会重新引入数据安全风险。
- 成本至少是修复的一个数量级以上。

### 4. 正反两方的最强论证

**「应该重建」的最强理由**

- Step 4-11（云端回写、云端 prepend 和 metadata）全部建立在这条接受链上，而这条链的核心问题是「接受一个提案意味着什么」**没有 owner**：4 份授权、3 个流水写入方、2 套 JSON 格式、UI 替它做决定。
- 在 967 行的 repository 和 1399 行的 dialog 上一点点挪，可能不如按类型化的结果（typed outcome）把这个子系统重新推一遍来得干净。
- 更要紧的是，防护机制已经失效过一次，修完凭什么就不再发生？

**「应该原地修」的最强理由**

- 侵蚀只有两天，集中在大约 6 个文件，没有 P0，主干分层完好。
- 修复的目标位置全都已经存在：`ports.py`、`AiReceiptInboxService`、domain 里的 `RECEIPT_STATUS_*`。
- 最关键的一点：**侵蚀的根本原因是闸门没有被执行，不是架构设计错了**。重建不能修好「没人看闸门」这件事；把闸门写进 closeout 硬条件才能。
- 重建还会把 R1 对照测试和十几次人工验收的证据全部作废。

**寓的判断**：**原地修，但要对接受子系统做「就地搬家」式的局部重写**，而不是零散打补丁。

1. 在 Step 4 之前插一个独立的修复包。
2. P1-1、P1-2、P1-5、P1-11 是小修，可以先做。
3. P1-3、P1-4、P1-6、P1-7 作为一个整体设计：「接受」变成 application 的用例，结果带类型，规范化挪到事务外面。
4. 修复包的封口条件：闸门 PASS、全量测试绿、闸门补上两个盲区（顶层文件、`src.*` 引用）。
5. **不要让 Step 4 在当前这条链上继续往上盖**。那样两周后就真的会变成值得重建。

### 5. 置信度和覆盖范围

**高置信**

- 闸门和测试的事实，包括逐个 commit 重跑追出来的变化时间线。
- AI 接受链的结论。关键几条我亲自对过代码：`result_json` 分叉、事务内做规范化、bootstrap 顶层引用 Qt、保存拆成两个事务、Reminder resume 复活已完成提醒。

**中置信**

- Reminder 的非原子写入细节，以及 `store_operation` 查 `request_id` 不看 actor 的问题。这两条来自子代理的阅读，我只抽查了一条。
- 写锁里的 GUI 自动保存确实会撞上 5 秒超时。这是按代码推断的，没有实际并发复现。

**看得不够深的地方**

- `web/` 下的 Milkdown JS 和 Python 之间的桥接协议：只列出了信号名，没有逐条对照。
- `deploy/oracle` 服务器端代码的内部质量。
- `migration/` 和 `exporting/`。
- 打包流程（`packaging/`、build 脚本）。
- 性能和内存（包括历史上那次 120GB 事件）。
- `tests_mcp` 的失败没有判定。
- 测试本身的质量只看了和结构相关的部分。

**方法说明**：三路深读（AI 写入链路、Reminder/Gale/legacy、UI/transport）由 Opus 子代理并行完成，寓自己跑了闸门、全量测试和历史 commit 重跑，并核对了上面所有标注「已核实」的结论。
